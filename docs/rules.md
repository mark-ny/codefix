## ASSERT_TUPLE

assert on a tuple is always true.

Parenthesising the condition and message creates a tuple, which is always truthy.

Bad:
```python
assert(x > 0, 'x must be positive')
```
Good:
```python
assert x > 0, 'x must be positive'
```

**False positives:** Tuples with more than two elements are reported without a fix.

## BARE_EXCEPT

Bare 'except:' block.

A bare except hides interrupts and genuine bugs. The fix narrows it to `except Exception:`, which still changes behaviour for BaseException subclasses, hence 'review'.

Bad:
```python
try:
    work()
except:
    handle()
```
Good:
```python
try:
    work()
except Exception:
    handle()
```

**False positives:** Handlers that end in a bare `raise` (cleanup then re-raise) are not reported.

## COMPARE_LITERAL

Use == / != to compare with a literal.

`is` compares object identity, which is unreliable for numbers and strings (and a SyntaxWarning).

Bad:
```python
if status is 200:
```
Good:
```python
if status == 200:
```

**False positives:** `is` with None/True/False/Ellipsis is correct and not reported.

## COMPARE_NONE

Use `is None` instead of `== None`.

None is a singleton; identity comparison is faster and not fooled by custom __eq__.

Bad:
```python
if value == None:
```
Good:
```python
if value is None:
```

**False positives:** Objects overriding __eq__ to compare equal to None (e.g. numpy arrays compare element-wise) change meaning; that is almost never intended.

## DUPLICATE_CODE

Duplicated code.

Structurally identical code (same AST, ignoring comments and formatting) should live in one place.

Bad:
```python
def a(x):
    ...

def b(x):
    ...  # same body
```
Good:
```python
# extract the shared logic
```

**False positives:** Only exact structural duplicates are detected; renamed variables are not matched.

## EXCEPT_PASS

Exception swallowed with 'pass'.

Silencing every exception makes failures invisible. Log, narrow the exception, or re-raise.

Bad:
```python
try:
    work()
except Exception:
    pass
```
Good:
```python
try:
    work()
except Exception:
    logger.exception('work failed')
```

**False positives:** `contextlib.suppress(SpecificError)` is the explicit alternative.

## INCONSISTENT_RETURN

Inconsistent return behaviour.

Mixing `return value` with bare `return` (or falling off the end) makes callers guess whether None is meaningful. The safe fix makes bare returns explicit (`return None`).

Bad:
```python
def f(x):
    if x:
        return 1
    return
```
Good:
```python
def f(x):
    if x:
        return 1
    return None
```

**False positives:** Functions annotated `-> None` and generators are skipped. Falling off the end is reported, not fixed.

## MISSING_DOCSTRING

Public function is missing a docstring.

Public functions and methods form an API; a docstring states the contract.

Bad:
```python
def area(w, h):
    return w * h
```
Good:
```python
def area(w, h):
    """Return the area."""
    return w * h
```

**False positives:** Private (`_x`) and dunder names, nested functions, overloads, property setters and test files are skipped.

## MUTABLE_DEFAULT

Mutable default argument.

Default values are evaluated once, so a list/dict/set default is shared by every call. The fix replaces the default with None and creates the object inside the function. It is 'risky' because callers may rely on the shared state, so tests are required.

Bad:
```python
def add(item, bucket=[]):
    bucket.append(item)
    return bucket
```
Good:
```python
def add(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket
```

**False positives:** Intentional caching via a mutable default is rare but real; add `# codefix: ignore[MUTABLE_DEFAULT]`. Type annotations are left untouched (consider `list | None`).

## RESOURCE_NO_CONTEXT

Resource opened outside a context manager.

Files opened without `with` stay open if an exception occurs before close().

Bad:
```python
f = open(path)
data = f.read()
f.close()
```
Good:
```python
with open(path) as f:
    data = f.read()
```

**False positives:** Not reported when the handle is returned, closed via ExitStack/closing, or later used in `with`.

## SHADOW_BUILTIN

Name shadows a built-in.

Rebinding names such as `list`, `id` or `type` makes the built-in unreachable in that scope and causes confusing errors later.

Bad:
```python
def f(list):
    return len(list)
```
Good:
```python
def f(items):
    return len(items)
```

**False positives:** Class attributes (e.g. ORM fields named `id`) are not reported.

## STRING_CONCAT_LOOP

String concatenation inside a loop.

Repeated concatenation copies the string each time (quadratic in the worst case). Collect parts in a list and use ''.join().

Bad:
```python
out = ''
for w in words:
    out += w
```
Good:
```python
out = ''.join(words)
```

**False positives:** CPython often optimises `s += x`, so small loops are fine. Detection is name/literal based.

## TYPE_COMPARE

Use isinstance() instead of comparing type().

isinstance() honours inheritance. The fix is 'review' because exact-type checks are sometimes intended.

Bad:
```python
if type(x) == int:
```
Good:
```python
if isinstance(x, int):
```

**False positives:** Use `type(x) is T` deliberately when subclasses must be excluded.

## UNDEFINED_NAME

Name is not defined in any visible scope.

Using a name that no scope defines raises NameError at runtime.

Bad:
```python
def f():
    return missing_name
```
Good:
```python
def f(missing_name):
    return missing_name
```

**False positives:** Skipped in files with `from x import *`. Lowered confidence when exec/eval/globals() are used.

## UNREACHABLE_CODE

Unreachable code.

Code after an unconditional return, raise, break or continue never runs.

Bad:
```python
def f():
    return 1
    print('never')
```
Good:
```python
def f():
    return 1
```

**False positives:** Only straight-line statement lists are analysed; `sys.exit()` is not treated as terminal.

## UNUSED_IMPORT

Imported name is never used.

Unused imports slow start-up, hide real dependencies and confuse readers. Removal is 'review' level because an import can have side effects or be a deliberate re-export.

Bad:
```python
import os
import sys

print(sys.argv)
```
Good:
```python
import sys

print(sys.argv)
```

**False positives:** Skipped in __init__.py, for names in __all__, `__future__` imports and imports guarded by try/except ImportError. Lines with trailing comments (e.g. `# noqa`) are reported but not fixed.
